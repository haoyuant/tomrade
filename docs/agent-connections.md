# Repository agent connections

A repository is connected in one of two ways.

**This machine only** writes the chosen agents' files into the checkout itself and lists them in `.git/info/exclude`, so nothing is committed, pushed or pulled: the same files as below, except that Claude Code's hooks and its approval of the `.mcp.json` server (`enabledMcpjsonServers`) go in `.claude/settings.local.json`. `CLAUDE.md` and `AGENTS.md` carry the instruction section too, so the agent reads the rules; one the repository already tracks is left as the team wrote it and the MCP server's instructions speak instead. A tracked file is never changed: its agent is skipped and the result says so (`tracked`). Codex still asks to trust the project and to review the hooks with `/hooks`, as for any project hooks. Start a new agent session afterwards. If the team's connection lands in the repository later, pulling it replaces these ignored files with the committed ones, and the exclude lines no longer matter.

**For the team** writes a `tomrade/connect` branch and offers a pull request. Merge it, update the checkout and open a new agent session. The committed instruction text applies only where the `tomrade` server is available, so a clone on a machine without Tomrade is told to carry on as usual. The URL names the Tomrade instance that generated it; another Tomrade opening the same project on another port (a development build, a teammate) sees the repository as connected to that one and does not ask to reconnect — only an address with another project id is "another instance".

Only the agents chosen for the repository get configuration, and only they decide whether it counts as connected. Until someone chooses, they are the agents installed on this machine (all of them when none is found); connecting keeps that choice with the repository in the project, so an agent installed or added to Tomrade later does not make it unconnected. A plugin engine that registers a connection writer (`ctx.codeLink.registerConnector`) is offered and detected the same way: Connect writes the file it names, and reads it back to say whether that agent tracks its sessions.

| Agent | Project configuration | Session reporting | Acts on Tomrade's answer |
| --- | --- | --- | --- |
| Claude Code | `.mcp.json`, `.claude/settings.json` | Lifecycle hooks, including start and end | Yes: a denied tool, context at start and after tools, a continued turn |
| Codex CLI | `.codex/config.toml` | Lifecycle hooks, including start and end; requires a hooks-capable version, a trusted project and review through `/hooks` | Yes, the same way (Codex reads Claude Code's hook output); a changed hook command needs `/hooks` again, as trust is tied to its hash |
| WorkBuddy | `.mcp.json`, `.codebuddy/settings.json` | Lifecycle hooks in Claude Code's format | Yes, as Claude Code |
| Pi | `.pi/extensions/tomrade.ts` | The extension reports the same events | A denied tool only |
| OpenCode | `opencode.json`, `.opencode/plugins/tomrade.js` | The plugin reports the same events | A denied tool only, as the tool's error |
| Cursor | `.cursor/mcp.json`, `.cursor/hooks.json`, `.cursor/hooks/tomrade` (`.cursor/hooks/tomrade.ps1` on Windows) | Lifecycle hooks, including start and end; its own sessions reach Tomrade once Settings → Cursor connects `~/.cursor/mcp.json`. The project server must be approved before Cursor loads it (see below) | No: its script swallows the answer, because Cursor's permission hooks block on any reply that is not in their own shape |
| Gemini CLI | `.gemini/settings.json` using `httpUrl` | No lifecycle hooks; followed through its MCP connection once it claims a ticket | No |

`CLAUDE.md` and `AGENTS.md` explain ticket ownership and the rule before a code change: look at the checkout's branch and whether the session holds a ticket; a session on a ticket goes on with it, and one whose checkout is already on a ticket's branch claims that key once and continues there, with no new ticket per request; a new piece of work the person asked for gets a ticket of its own (`create_item`, then `claim_ticket`) and is made on the claim's branch without asking; when it is unclear a ticket is wanted, the agent asks first, and on the person's word to go without one calls `work_without_ticket`; never an edit or a commit on the default branch, or another ticket's branch, without one of these. The MCP server's instructions say the same to every client, including those with no instruction file. Codex also gets the `tomrade-sync` skill. In those two files Tomrade writes only between `<!-- BEGIN TOMRADE -->` and `<!-- END TOMRADE -->`; a `## Tomrade` section from before the markers is replaced up to the next heading of the same or higher level, and marked, when the repository is connected again.

The committed hooks of Claude Code, Codex and WorkBuddy leave Tomrade's answer on stdout, so `/sessions/event` answers as the session's own hooks do. Tomrade itself answers an outside session in a project repository in two ways: at `SessionStart`, context saying the session holds no ticket and what to do before changing code; and at `PreToolUse`, a refusal of the first file edit (`Edit`, `Write`, `MultiEdit`, `NotebookEdit`, `apply_patch` and the like) or history-writing git command (`commit`, `push`, `merge`, `rebase`, `cherry-pick`, `revert`, `am`, `apply`) made while the session holds no ticket and has not recorded the person's word to go without one, with the ways on in the reason: when the checkout's branch names a ticket, to claim that key and go on there; otherwise a ticket of its own, a question to the person, or their word. The branch is read from `.git/HEAD` only when there is something to say. A file outside the folder the agent runs in is not held. Nothing is held when Tomrade is down (curl says nothing and the hook exits 0), when the hooks are not trusted or not loaded, in a session Tomrade started (it has its ticket), or through an agent whose hooks only observe. `work_without_ticket` records the person's words on the session (`withoutTicket`); a later `claim_ticket` clears it. A claim also reports `sharedCheckout`: other live sessions in the same folder, with a convention to take the branch to a worktree rather than change files beside them.

Cursor loads a project MCP server only after it is approved. The IDE asks once when the folder is opened. `cursor-agent` in a terminal does not ask: run it once with `--approve-mcps`, or approve the server through `cursor-agent mcp`, or it starts without the `tomrade` server — no tools, no ticket, and the rules in `AGENTS.md` cannot be acted on. The approval is kept per project, so it is needed once rather than on every run. `cursor-agent mcp list` says whether the server is loaded or still `not loaded (needs approval)`.

An agent Tomrade did not start carries no session token, so its claim is tied to its MCP connection (the `Mcp-Session-Id` every Streamable HTTP client sends), whatever the agent: `claim_ticket` takes the hooks session on that repository that no one else holds, or starts one followed only through the connection, and the calls after it on that connection — `note_progress`, `link_code`, `report_merge_blocked` — need no key. A session followed only through its connection ends when the connection closes. After a reconnect or a Tomrade restart the connection is new: the agent names its ticket once (`key`) and the session is found again. A session that already holds a ticket is never handed to another terminal's claim. A claim on a ticket another live session is working (heard from within the hour, not waiting on the person's merge) changes nothing and answers `claimed: false` with who holds it; `takeOver: true` claims it anyway. `release_ticket` gives back a ticket claimed by mistake: a session made only for that claim ends, and the ticket's status stays. The result's `tracking.tracked` says whether progress notes will land. Existing `notify` commands and unrelated server definitions are retained. No file is rewritten in a way that loses what is in it: JSON with comments or trailing commas is read but not rewritten, a file that cannot be read is left alone, and Codex hooks written as inline arrays are not extended. That agent (for Codex, its hooks) is skipped and the result says why; the other agents still connect.

Codex hooks carry the `X-Tomrade-Agent: codex` header and the native `session_id`, `cwd` and `hook_event_name` payload. Tomrade records the source as Codex, independently of Claude session IDs. The generated command requires `curl`, finishes within two seconds and does not block work when Tomrade is offline. Codex's own hook trust policy remains in control. Older versions without lifecycle hooks should be upgraded; `notify` alone only reports completed turns and cannot provide session start/end. Codex loads a project's `.codex/config.toml` (its hooks and its `tomrade` server) and `AGENTS.md` only when it starts inside the project: started from the home folder, it has neither, and only a user-level server reaches Tomrade.

The hooks run on macOS, Linux and Windows without Git Bash. Claude Code, Codex and WorkBuddy get one command that sh, bash, zsh, Git Bash and PowerShell all read the same way: Claude Code runs hooks in Git Bash on Windows, or in PowerShell where Git Bash is missing, and Codex runs them in PowerShell. The first step keeps its output in a variable (`set tomrade "$(…)"`, which PowerShell reads as `Set-Variable`); curl's answer stays on stdout for the agent, and the hook exits 0. Repositories connected before this carry the command that swallowed the answer too, and still count as connected; connecting again replaces it. Windows PowerShell's `curl` alias is removed first so that `curl.exe` (part of Windows 10 1803 and later) runs. `cmd.exe` is not supported; Codex falls back to it only when it finds no PowerShell. Cursor on Windows wraps every hook in PowerShell and pipes the payload in. For a command that names a path without an extension, it runs the `.ps1` file beside that path, so `.cursor/hooks.json` names `.cursor/hooks/tomrade`. Other systems run that POSIX script directly, so it is committed as executable even from a Windows checkout. Repositories connected before keep their POSIX-only hooks (`sh .cursor/hooks/tomrade.sh` for Cursor) and still count as connected; connecting again replaces them.

For other agents with Streamable HTTP MCP support, manually add a server named `tomrade` using the project URL shown in Repository settings. The connection does not create configuration for those agents. Reading `AGENTS.md` supplies instructions only; it does not itself grant tool access or session tracking.

Configuration references checked on 2026-10-15 (hook shells on 2026-10-18):

- [Codex hooks and trust](https://learn.chatgpt.com/docs/hooks): project inline TOML hooks and their input fields.
- [Codex notify](https://learn.chatgpt.com/docs/config-file/config-advanced#notifications): turn-completion notifications.
- [Cursor MCP](https://cursor.com/docs/mcp): project `.cursor/mcp.json`, remote `url`.
- [Cursor hooks](https://cursor.com/docs/agent/hooks): project `.cursor/hooks.json`, version 1; payloads checked against cursor-agent 2026.10.16 on 2026-10-17. Cursor skips a hook whose command names `curl` or `wget`, so the hook runs a committed script that does.
- [Gemini CLI MCP](https://geminicli.com/docs/tools/mcp-server/): project `.gemini/settings.json`, Streamable HTTP `httpUrl`.
- [Claude Code hooks](https://code.claude.com/docs/en/hooks): shell-form hooks run in `sh -c`, Git Bash on Windows, or PowerShell where Git Bash is missing.
- Codex runs hook commands in the session's shell: the user's shell elsewhere, and PowerShell on Windows (`pwsh`, then `powershell`, then `cmd.exe`). This comes from its source (`codex-rs/hooks`), because the hooks page does not say. It also accepts a `commandWindows` override, which Tomrade does not need.
- Cursor on Windows: cursor-agent 2026.10.16 runs a hook as `… | & { $input | <command> }` in `pwsh` or `powershell -ExecutionPolicy Bypass`, and resolves a path without an extension to `.ps1`, `.exe`, `.bat` or `.cmd`. This was read from its bundle, because the hooks page does not say.
